# Test Audit

Writing tests without strict criteria creates maintenance debt. Code coverage alone is not test quality. Every test must protect an observable behavior at the strongest architectural boundary.

## 1. Authoring Gate

Before adding or accepting any new test, answer these four questions:

1. **Observable Behavior**: Does this test protect an external contract, system invariant, or user-observable output rather than internal implementation details?
2. **Credible Regression**: What realistic failure or bug would cause this test to fail? (A valid test must fail red before the fix for the intended reason, and turn green after).
3. **Strongest Boundary**: Why does existing test coverage miss this? Assign each contract to one primary owner at its strongest boundary. Do not duplicate the exact same assertion across every crossed layer.
4. **No Test-Only Production Seams**: Does this test require adding exports, flags, wrappers, or injection hooks into production code that have no production callers? If so, reject the seam and test through the real interface.

If any answer is unsatisfying, do not write or keep the test.

## 2. Junk Patterns to Reject

Reject or remove tests exhibiting any of these anti-patterns:

- **Mock Inflation**: Mocks that supply the exact logic being asserted, or mocks so extensive that the test only exercises the mocking library itself.
- **Testing Private Helpers & Call Shapes**: Asserting private function outputs, call counts, or parameter shapes that duplicate public boundary tests. Tests must survive refactoring without breaking when observable behavior remains unchanged.
- **Fabricated Fixtures**: Fixtures that simulate receipt IDs, database persistence, or event sequences that production code never actually writes or emits.
- **Redundant Layer Replays**: Testing the same business logic at the unit, service, controller, and router layers simultaneously with mocked collaborators. Keep proof at the real boundary.
- **Vacuous or Misleading Asserts**:
  - Tests with no assertions (assertion-free smoke tests).
  - If the test would still pass when every function returned nothing, throw it out.
  - Self-comparisons or expected values generated by the subject under test.
  - Negative tests passing because of an early unrelated guard rather than the condition under test.
  - Test descriptions claiming behaviors that assertions never exercise.
- **Production Code Contamination**: Helper methods, bypass parameters, or reset functions added to production classes solely to make testing easier.

## 3. Proportional Proof Policy

Test proportional to the scope of change:

- **Targeted Local Proof**: Run only the tests directly covering touched code and modules. Do not block local work running the entire test suite when a targeted run proves the change.
- **Docs and Formatting Only**: Changes touching only documentation, comments, or formatting bypass runtime test suites. Run only linting or markup checks.
- **Structural and Build Verification**: Changes affecting build tools, package configurations, or dependency imports must run the project build/compile step.
- **Shared Libraries and Interfaces**: When changing shared utilities or public interfaces, test against representative consumer modules rather than attempting an exhaustive full-repo sweep.

## 4. Defect and Flakiness Hygiene

- **Reproduce Before Fixing**: For bug fixes, reproduce the failure with a minimal test at the real entry point first. Prove it fails red, apply the surgical fix, then prove it turns green.
- **Never Rerun Just for Green**: Rerunning tests hoping a flaky test turns green without code changes does not prove a fix. Investigate ordering dependencies, timing assumptions, or shared mutable state.
- **Anti-Masking**: Never resolve test failures by inflating timeouts, swallowing exceptions, weakening assertions, or expanding mocks. Fix the underlying root cause.
- **Clean State**: Tests must execute in isolated temporary environments and leave no residual files, ports, or modified persistent state behind.

## 5. Campaign Mode (Pruning Subsystems)

When cleaning up large legacy test suites or removing bloat across an entire module:
- Follow the 8-step structured process in [campaign.md](references/campaign.md).
- Use a read-only 4-mark ledger (`R` retain, `F` fix assertion, `C` consolidate, `D` delete).
- Designate primary keeper suites and verify retained coverage with mutation testing.
