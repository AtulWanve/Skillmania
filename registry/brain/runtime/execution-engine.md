# Execution Engine (Phase 11)

Generates implementation changes strictly based on the approved plan. Runs after [[system/planner|Planning]], feeds into [[runtime/static-validator|Static Validator]].

## Responsibilities

- Execute code modifications according to the approved plan
- Respect [[standards/CONTEXT|project standards]] and domain rules
- Maintain surgical scope: avoid unrelated refactoring or cleanup
- Preserve existing architecture and conventions
- Execute deterministically without evaluation: no review occurs during execution

## Input Schema (Plan Ingestion)

The Execution Engine ingests an `ExecutionPlan` produced by [[system/planner|Planner]]:

| Field | Type | Description |
|-------|------|-------------|
| `goal` | `string` | Target outcome and acceptance criteria |
| `affectedModules` | `string[]` | Subsystems and architectural domains touched |
| `executionOrder` | `PlanStep[]` | Ordered sequential operations to execute |
| `estimatedComplexity` | `"low" \| "medium" \| "high"` | Assessed implementation difficulty |
| `riskAnalysis` | `RiskReport` | Failure modes and containment guidance |
| `testingStrategy` | `string[]` | Test suites and validation commands |
| `rollbackStrategy` | `"none" \| "revert" \| "migration"` | Action to execute if failures occur |
| `estimatedFiles` | `string[]` | Allowlist of target file paths |
| `context` | `ContextPayload` | Active memory and graph node references from [[runtime/context-loader|Context Loader]] |

## Output Diff Schema

Upon completion or failure, the Execution Engine returns an `ExecutionResult` object:

| Field | Type | Description |
|-------|------|-------------|
| `status` | `"success" \| "partial" \| "failed"` | Outcome of the execution pass |
| `taskId` | `string` | Stable task identifier |
| `filesModified` | `string[]` | List of pre-existing files modified |
| `filesCreated` | `string[]` | List of brand-new files written |
| `filesDeleted` | `string[]` | List of removed files |
| `diffs` | `FileDiff[]` | Structured patch details per file |
| `executionLog` | `string[]` | Step-by-step transcript of executed changes |
| `errorMessage` | `string \| null` | Error details if execution halted unexpectedly |

### File Diff (`FileDiff`)

| Field | Type | Description |
|-------|------|-------------|
| `filePath` | `string` | Target file path |
| `operation` | `"create" \| "modify" \| "delete"` | Applied file mutation type |
| `linesAdded` | `number` | Count of inserted lines |
| `linesRemoved` | `number` | Count of deleted lines |
| `patch` | `string` | Unified diff representation of the change |

## Surgical Scope Rules

The Execution Engine enforces strict surgical boundaries:

1. **Target Allowlist**: Modifies only files listed in `estimatedFiles` and steps explicitly defined in `executionOrder`.
2. **No Speculative Refactoring**: Never reformat adjacent code, optimize untouched logic, or rename unrelated variables/types.
3. **No Stylistic Churn**: Match existing codebase formatting, indentation, and conventions exactly.
4. **No AI Attribution**: Never introduce AI attribution markers (such as `Co-Authored-By`, `Generated by AI`, or em dashes in comments/code).
5. **Deterministic Mutation**: Apply targeted string replacements rather than rewriting entire files when performing edits.

## Error-Handling and Rollback Protocols

1. **Pre-flight Checks**: Verify target directories exist and target files are writable before starting mutations.
2. **Step-by-Step Failure Isolation**: If a step fails (e.g., target file missing, syntax parsing error, or conflict):
   - Immediately halt further execution steps.
   - Set `status = "failed"` and populate `errorMessage`.
3. **Surgical Rollback**:
   - Apply the prescribed `rollbackStrategy` (`"none"`, `"revert"`, or `"migration"`).
   - Revert only the specific lines or files touched during the failed execution pass.
   - Never perform destructive git commands (`git reset --hard`, `git clean`, or `git checkout --`) that could discard concurrent, uncommitted user work.
4. **Diagnostic Handoff**: Emit the `ExecutionResult` back to the [[runtime/orchestrator|Orchestrator]] to feed into retry or escalation workflows.
